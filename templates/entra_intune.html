01My Lab Environment

I built my own Microsoft 365 Business Premium lab environment to gain hands-on experience with Microsoft Entra ID and Microsoft Intune.

The purpose of the lab was not simply to learn where settings are located in the administrative portals. I wanted to understand the complete endpoint lifecycle:

Identity → Device Registration → Enrollment → Configuration → Application Deployment → Security → Compliance → Conditional Access → Troubleshooting → Device Retirement or Reset

I used Windows virtual machines and test devices so that I could deploy policies, intentionally create problems, observe the results, and troubleshoot them.

My professional experience has primarily been with traditional Active Directory and enterprise endpoint support. Intune and Entra ID are areas in which I have been building hands-on experience through this lab.

02Microsoft Entra ID

Microsoft Entra ID is Microsoft's cloud identity and access management platform.

I used Entra ID to manage:

  • Users
  • Groups
  • Administrative roles
  • Device identities
  • Authentication
  • MFA
  • Microsoft Intune integration
  • Conditional Access

One important concept I learned is that Microsoft Entra ID is not simply a cloud version of traditional Active Directory Domain Services.

Traditional AD DS uses concepts such as:

  • Domains
  • Domain Controllers
  • Organizational Units
  • Group Policy
  • LDAP
  • Kerberos
  • Domain Join

Entra ID is designed around cloud identities, cloud applications, modern authentication, device identities, and access control.

03Users, Groups, and Administrative Roles

I created users in my Entra tenant and learned how identities created in Entra ID are also used across Microsoft 365 and Intune.

I also worked with different types of groups.

User Groups

These can be used to assign:

  • Applications
  • Configuration
  • Compliance-related settings
  • Access policies

Device Groups

These allow policies and applications to follow the device rather than a particular user.

Dynamic Groups

Dynamic membership allows devices or users to be automatically placed into groups based on defined attributes.

This helped me understand the difference between:

Who should receive something?

and

Which device should receive something?

This distinction becomes very important when designing Intune assignments.

04Microsoft Intune

Microsoft Intune is Microsoft's cloud-based endpoint management platform.

I learned to think about Intune as a device lifecycle management system, rather than simply a configuration tool.

A simplified lifecycle is:

Enroll → Configure → Protect → Deploy → Evaluate → Maintain → Retire/Reprovision

Intune can manage:

  • Device enrollment
  • Device configuration
  • Applications
  • Security settings
  • Compliance
  • Windows updates
  • Encryption
  • Remote actions
  • Device lifecycle operations

It also integrates closely with Entra ID and Conditional Access.

Back to top ↑

05Entra Join vs. Intune Enrollment

I learned that device identity and device management are related but separate concepts.

A Windows computer can have an identity in Entra ID, while Intune provides the MDM management layer.

For a corporate Windows device, a common modern workflow is:

Windows device → Microsoft Entra Join → Intune enrollment → Configuration and applications → Compliance evaluation → Conditional Access

I also learned that this is different from traditional Active Directory Domain Join.

06Windows Autopilot

I created a Windows Autopilot deployment in my lab.

Autopilot allows an organization to prepare a Windows computer for corporate use without IT manually creating and applying a traditional custom Windows image to every computer.

The general workflow I learned was:

Hardware identity → Autopilot registration → Deployment profile → Windows OOBE → User authentication → Entra Join → Intune enrollment → Applications and policies → Corporate-ready endpoint
Back to top ↑

07Autopilot Hardware Hash

I learned how Windows Autopilot identifies a particular physical device.

The hardware hash is not simply one hash shared by every computer of the same model.

It represents hardware information from the individual device.

Therefore:

Laptop A → unique Autopilot device identity Laptop B → different Autopilot device identity

even if both computers are the same make and model.

In my lab, I collected the hardware information and imported it into Windows Autopilot using CSV.

In an enterprise environment, this step can often be performed by the OEM, reseller, or hardware supplier.

For example:

Company orders laptops → OEM/reseller registers the devices for the company's tenant → Devices are shipped directly to users → Users power them on → Autopilot recognizes the devices → Corporate provisioning begins

This is one of the major advantages of modern endpoint provisioning.

Back to top ↑

08Windows Autopilot Devices vs. Intune Managed Devices

I learned that the Autopilot device record and the Intune managed-device record represent different concepts.

The Autopilot record identifies the device as a device registered for Windows Autopilot.

The Intune device record represents the actively managed endpoint.

Completing an Autopilot deployment does not mean that the Autopilot registration disappears.

The device may remain registered for future reprovisioning.

This distinction helped me understand why device lifecycle actions must be selected carefully.

09Autopilot Deployment Profile

I created and assigned an Autopilot deployment profile.

The deployment profile determines how Windows OOBE behaves and how the corporate device is provisioned.

The goal is to reduce the number of configuration decisions that the end user must make.

Instead of IT manually configuring each laptop, the organization defines the desired provisioning experience centrally.

10Enrollment Status Page — ESP

I configured and tested the Enrollment Status Page.

ESP can prevent the user from reaching the Windows desktop before important provisioning requirements have been completed.

Conceptually:

User signs in → Device enrolls → Required policies/apps are processed → ESP monitors provisioning → User reaches desktop

This is useful because a computer should not necessarily be considered ready simply because Windows can display a desktop.

For example, IT may require security software, management components, or other critical applications before the endpoint becomes operational.

This included working with:

  • Microsoft Store applications
  • Company Portal
  • Win32 applications
  • Required applications
  • Available applications
  • Application assignments
  • Detection rules

I learned that assigning an application does not mean that the application immediately appears on the endpoint.

The process involves:

Assignment → Device/user check-in → Policy received → Applicability evaluation → Detection → Download → Installation → Detection again → Reporting

12Required vs. Available Applications

A Required application is automatically installed when the device or user meets the assignment requirements.

An Available application can be offered through Company Portal so that the user can choose to install it.

This provides a useful balance between standardization and user choice.

For example:

Security software → Required

while

Optional productivity utility → Available

may make more sense.

13Win32 Application Deployment

I packaged and deployed Win32 software through Intune.

This taught me that application deployment involves more than simply uploading an installer.

I had to think about:

  • Installation commands
  • Uninstallation commands
  • Installation context
  • Requirements
  • Detection rules
  • Assignments
  • Return codes

The detection rule is especially important because Intune needs a reliable way to determine whether the application actually exists after installation.

14Application Detection

I investigated application detection using the Intune Management Extension logs.

For example, Intune checked for an executable associated with an application.

Before installation:

Detection → NotDetected

After successful installation:

Detection → Detected

This demonstrated an important troubleshooting concept:

Installation and detection are separate operations.

An installer could theoretically run successfully while Intune still reports a failure if the detection rule is incorrect.

Therefore, when troubleshooting an Intune application deployment, I would check:

  1. Assignment
  2. Applicability
  3. Download
  4. Installation
  5. Exit code
  6. Detection rule
  7. Intune Management Extension logs
  8. Intune reporting

15Intune Management Extension

This gave me a much better understanding of what happens behind the Intune portal.

Instead of only seeing:

Installed / Failed / Pending

For application troubleshooting, I learned to look for information related to:

  • Policy retrieval
  • Application detection
  • Applicability
  • Download

  • Enforcement state
  • Error codes
  • Detection after installation

This is particularly useful when the Intune portal does not provide enough information to identify the root cause.

16Configuration Profiles

Configuration profiles tell managed devices:

Examples include:

  • Microsoft Edge settings

This helped me understand the relationship between traditional Group Policy and modern MDM.

They are not identical technologies, but conceptually both can centrally define endpoint configuration.

17Configuration vs. Compliance

One of the most important concepts I learned was the difference between configuration and compliance.

Configuration

“Configure the device this way.”

Compliance

“Check whether the device meets this requirement.”

For example:

A configuration policy may configure BitLocker.

A compliance policy may check whether encryption is enabled.

These are different functions.

A device can therefore be evaluated as:

Compliant

19BitLocker

I configured and verified BitLocker in my Windows lab.

I worked with:

  • TPM
  • BitLocker encryption
  • XTS-AES
  • Recovery information
  • Compliance requirements
  • Local verification using Windows tools

I learned an important security principle:

Remote management actions should not be considered a substitute for encryption.

If sensitive information is stored on an endpoint, BitLocker should already be protecting the data before a device is lost or stolen.

The security model should not depend on successfully sending a remote wipe command after the incident.

22Corporate Device Identification

Windows Autopilot registration is one strong mechanism for establishing that a Windows computer belongs to the organization.

In a real enterprise environment, an OEM or reseller may register corporate devices before they reach the employee.

Therefore the organization already has knowledge of the device before the employee begins using it.

This creates a much stronger trust model than simply allowing any Windows computer to enroll.

23BYOD Enrollment Restrictions

I created Windows enrollment restrictions for a BYOD scenario.

The default policy was designed to block personally-owned Windows enrollment.

I then created a controlled exception for a specific user/group.

The concept was:

Default position → Personal devices blocked
Approved exception → Personal enrollment permitted

This taught me that BYOD should not simply mean:

“Anyone can enroll any personal computer.”

Instead, enrollment should be deliberately controlled.

24Enrollment Restriction Priority

I learned that enrollment restrictions have priority.

A specific exception policy can have a higher priority than the default restriction.

Conceptually:

Priority 1 — Approved BYOD exception ↓ Default — Personal Windows devices blocked

This allows an organization to maintain a restrictive default while supporting documented exceptions.

25Assignment Filters

I created an Intune Assignment Filter based on device ownership.

The filter used the concept:

deviceOwnership = Personal

This allowed policies to distinguish personal devices from corporate devices without creating unnecessary additional groups for every assignment scenario.

I learned that a filter does not decide whether a device is Personal by itself.

It evaluates an attribute that Intune already knows about the device.

Conceptually:

Device enrolled → Intune determines/records ownership → Ownership attribute = Personal → Assignment filter evaluates the attribute → BYOD-specific policy applies

26Designing a Restricted BYOD Model

Instead of treating BYOD as equivalent to a corporate computer, I designed the scenario around minimum necessary access.

The security philosophy was:

A personal computer should receive only the access and configuration required for the approved business purpose.

For a highly restricted scenario, a personal endpoint might only be allowed to access specific remote-work resources such as a VPN and virtual desktop environment rather than storing sensitive corporate information locally.

This follows the principle of minimizing corporate data exposure on unmanaged or personally-owned hardware.

27Conditional Access

I created a Conditional Access policy requiring a compliant device to access a selected Microsoft 365 resource.

This connected several previously separate concepts:

Identity → Device → Compliance → Application = Access decision

This was one of the most important parts of the lab because it demonstrated how Intune and Entra ID work together.

28Configuration → Compliance → Conditional Access

I use this simple model to remember the relationship:

Configuration

Do this.

Compliance

Are you meeting the requirement?

Conditional Access

Based on those signals, should access be allowed?

For example:

Intune configuration → security settings applied
Compliance policy → endpoint evaluated
Conditional Access → compliant device required
Microsoft 365 → access allowed or denied
Back to top ↑

29Conditional Access Report-Only Mode

I tested Conditional Access in Report-only mode before enforcing the policy.

This is an important operational practice.

Instead of immediately blocking users, Report-only allows IT to evaluate what the policy would have done.

This reduces the risk of accidentally locking out legitimate users.

The workflow is:

Create policy → Report-only → Test → Review Sign-in Logs → Confirm expected behavior → Adjust policy if necessary → Enforce only after validation

30Conditional Access — Compliant Device Test

I tested access from a recognized compliant device.

The Sign-in Logs showed that the Conditional Access policy matched and the required grant control was satisfied.

31Conditional Access — Unknown Device Test

I then tested access from another Windows computer that had not been enrolled as the managed BYOD device.

The Sign-in Log showed:

Device: Unknown

and:

Grant Controls: Not satisfied

because the policy required a compliant device.

Since the policy was still in Report-only mode, the user could still sign in.

However, the log showed that the policy would have blocked the access if it had been enforced.

This gave me practical experience interpreting Conditional Access results rather than only configuring the policy.

33Device = Unknown

A particularly useful lesson was understanding:

Device: Unknown

This does not simply mean:

“The device is noncompliant.”

It can mean that Entra Conditional Access cannot identify a managed device identity for that sign-in.

Therefore there is an important troubleshooting distinction between:

Known device + Noncompliant

and

Unknown device + Compliance cannot be established

Both may fail a “Require compliant device” control, but for different reasons.

36Sync

Sync requests that the managed endpoint check in with Intune and retrieve current policy.

This can be useful when:

  • A new application has been assigned
  • A policy has changed
  • Compliance needs to be reevaluated
  • Troubleshooting delayed policy delivery

However, I also learned that cloud management is not always instantaneous.

Assignments and device state can take time to propagate.

37Restart

A remote restart can be useful operationally, but user impact must be considered.

In a production environment, especially a mission-critical environment, IT should understand:

  • Who is using the computer?
  • What application is running?
  • Can the operation be interrupted?
  • Has the user been notified?
  • Is there a maintenance window?

Technical capability does not automatically mean that an action should be executed immediately.

38Autopilot Reset

I tested Autopilot Reset.

The goal of Autopilot Reset is to prepare an existing corporate Autopilot device for reuse while maintaining its organizational provisioning relationship.

Conceptually:

Existing corporate device → Reset → User-specific state removed → Corporate provisioning retained → Device prepared for another user

However, the lab also showed me important operational limitations.

The reset can be disruptive, and once initiated, IT must carefully consider the user experience and physical device state.

A remote reset should therefore be treated as a controlled operational change, not a casual help-desk action.

39Operational Lesson from Autopilot Reset

One of my biggest lessons from testing Autopilot Reset was:

Endpoint management is not only about whether a command technically works. It is also about whether the action is operationally appropriate.

Before resetting a production computer, I would want to verify:

  • Correct asset/device
  • Correct user
  • User has saved work
  • Required data is synchronized
  • Business operation can tolerate the interruption
  • Recovery/provisioning requirements are understood
  • Someone can intervene locally if necessary

This is especially important in mission-critical environments.

40Fresh Start

I learned that Fresh Start and Autopilot Reset serve different purposes.

Fresh Start is generally associated with reinstalling/refeshing Windows while removing unnecessary software and retaining the device's management relationship.

Autopilot Reset is more specifically associated with returning an existing managed Autopilot endpoint to a reusable organizational state.

The correct choice depends on the business objective.

41Retire

Retire is particularly important for BYOD.

The goal is to remove the organization's management relationship and managed corporate data/settings where supported without treating the employee's personal computer as corporate property.

Conceptually:

Employee personal device → Intune enrollment → Business use → Employee leaves / BYOD access ends → Retire → Corporate management removed → Personal device remains

This is fundamentally different from wiping a corporate computer.

Back to top ↑

42Wipe

Wipe is a much more destructive action.

It is appropriate for scenarios where the organization intends to reset the device rather than simply remove management.

I also learned an important security limitation:

Remote wipe should not automatically be treated as forensic-grade data sanitization.

For highly sensitive corporate assets being disposed of, the organization should follow its formal media sanitization and disposal policy.

BitLocker encryption, secure handling, and appropriate storage-media destruction or sanitization procedures remain important.

Back to top ↑

43Delete

Deleting a device record and sanitizing the physical storage device are different operations.

Deleting a management record does not mean that the storage media has been securely erased.

This distinction is critical:

Management-plane cleanup ≠ Data sanitization

A device can disappear from a management console while data still physically exists on the endpoint.

44Security Lesson: Encryption Before Loss

My previous operational experience strongly influenced how I think about this.

The best time to protect data is before a laptop disappears.

Therefore an enterprise should continuously enforce and monitor security controls such as:

  • BitLocker
  • Appropriate authentication
  • Secure Boot
  • Firewall
  • Endpoint protection
  • Compliance

The security strategy should not begin after somebody reports:

“The laptop has been stolen.”

46Troubleshooting Method

I try to troubleshoot Intune problems by determining which layer failed.

For example, if an application does not appear:

1. Identity
  • Is the correct user signed in?
2. Enrollment
  • Is the endpoint actually enrolled?
3. Device identity
  • Is the correct device visible in Entra and Intune?
4. Assignment
  • Is the user/device in the correct group?
5. Filter
  • Does the assignment filter match?
6. Policy delivery
  • Has the endpoint checked in?
7. Applicability
  • Does the endpoint meet the requirements?
8. Installation
  • Did the installer execute?
9. Detection
  • Does Intune recognize the application afterward?
10. Reporting
  • What does Intune report?
11. Local logs
  • What does the Intune Management Extension say actually happened?

This prevents me from immediately assuming that “Intune is broken.”

I think of it in terms of the complete device lifecycle: enrollment, configuration, application deployment, security, compliance, remote management, and eventually retirement or reprovisioning. In my lab, I used Entra ID together with Intune for device identity, MFA, groups, and Conditional Access. My professional background is primarily with traditional Active Directory, so I also understand that Entra ID and AD DS are related identity technologies but are not the same thing.”

52Short Interview Answer — “Explain Autopilot”

“Windows Autopilot is a cloud-based Windows provisioning technology. Instead of IT manually imaging every computer, a corporate device can be registered with Autopilot, often by the OEM or reseller. When the user powers on the device and goes through OOBE, the device can receive the organization's deployment profile, join Entra ID, enroll into Intune, and receive the required applications and policies.”

53Short Interview Answer — “Configuration vs. Compliance vs. Conditional Access”

“I think of configuration as ‘Do this,’ compliance as ‘Are you meeting the requirement?’ and Conditional Access as ‘Based on that information, should you be allowed to access the resource?’ For example, Intune can configure security settings, a compliance policy can evaluate the endpoint, and Conditional Access can require that compliant state before allowing access to Microsoft 365.”
Back to top ↑

54Short Interview Answer — “How Would You Troubleshoot Intune?”

“I would first determine which layer is failing instead of immediately changing settings. I would verify enrollment and device identity, then check group membership, assignments and filters, policy status, and the device's last check-in. For application deployment I would also check applicability, installation status, detection rules, and the Intune Management Extension logs on the endpoint. For access issues involving Conditional Access, I would use the Entra Sign-in Logs to determine exactly which condition or grant control was not satisfied.”

55Most Important Lessons from the Lab

The biggest lesson I learned is that Intune is not a collection of isolated buttons.

The components form a system:

Entra ID establishes identity.
Autopilot establishes the provisioning workflow.
Intune manages the endpoint.
Configuration defines the desired state.
Applications provide the required software.
Compliance evaluates security posture.
Conditional Access uses identity and device signals to protect resources.
Logs and reporting explain what actually happened.
Lifecycle actions determine what happens when the device changes users, leaves management, or must be rebuilt.

And most importantly:

Good endpoint management is not just about making a technical command work. It is about protecting the organization while minimizing disruption to the user and the business operation.
